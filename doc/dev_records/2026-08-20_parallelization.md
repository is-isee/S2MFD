# スレッド並列化の検討と実測 (2026-08-20)

Rempel (2006) 再現を 48^2 より細かい格子で回したいという要求から、
ソルバの並列化を検討した。結論を先に書くと

> **効くのは 100^2 格子以上、かつスレッドは 2-4 で頭打ち。**
> 64^2 を多数流すときは逐次のままプロセス並列にするほうが速い。

環境変数 `S2MFD_PARALLEL` で切り替える (既定はオフ)。

```bash
S2MFD_PARALLEL=3 python run.py     # 3 スレッド
```

---

## 1. まず何が遅いのかを測る

`DynamicSolver.rhs()` の内訳 (numba カーネルのみ計時):

```
64x64:    合計 2.241 ms/step (1.120 ms/rhs)
   SLD (子午面)   0.1793 ms (16.0% of rhs)
   viscous        0.1725 ms (15.4%)
   momentum_rhs   0.0710 ms ( 6.3%)
   特性速度(numpy) 0.0658 ms ( 5.9%)
   angmom_rhs     0.0588 ms ( 5.2%)
   entropy        0.0378 ms ( 3.4%)
   mass_rhs       0.0180 ms ( 1.6%)
   (合計)         0.6031 ms      <- rhs の 54% しかない
108x144:  合計 8.798 ms/step (4.399 ms/rhs)、カーネル 2.1426 ms (49%)
```

**カーネルは半分しかない。**残り半分は numpy レベルのオーバーヘッドで、
その大半は `rhs()` が毎回 9 本の `np.zeros(self.shape)` を確保して
いたこと。作業配列を `DynamicSolver.__init__` で確保して使い回すよう
にした結果:

```
64x64    2.241 -> 2.198 ms/step  (2%)
108x144  8.798 -> 8.012 ms/step  (9%)
```

大きい格子ほど効くのは、確保コストが配列サイズに比例するのに対し
Python 側の呼び出し回数は同じだから。**期待より小さい**ので、
残りは `conserved()` / `set_primitive_from_conserved()` /
`_update_characteristic_speed()` / `step()` の
`a + dt*b` 型の一時配列に散っていると思われる (未着手)。

## 2. スレッド並列: 最初に 64 スレッドで測って誤った結論を出しかけた

代表カーネル (SLD の動径フラックス) を `prange` 化して、
利用可能な 64 論理コア全部で測ると:

| 格子 | 逐次 | 並列 (64 スレッド) | 速度比 |
|---|---|---|---|
| 64x64 | 39 us | 114 us | **0.34x** |
| 108x144 | 140 us | 127 us | 1.10x |
| 258x290 | 946 us | 158 us | 5.98x |

ここで「現行格子では並列化は無駄」と結論しかけたが、
**スレッド数を振っていなかった**のが誤り (ユーザ指摘)。振り直すと:

| スレッド | 64x64 | 108x144 |
|---|---|---|
| 逐次 | 39.1 us | 145.4 us |
| 1 | 42.1 (0.93x) | 169.6 (0.86x) |
| 2 | 43.4 (0.90x) | 87.4 (**1.66x**) |
| 3 | 40.8 (0.96x) | 67.1 (**2.17x**) |
| 4 | 35.1 (**1.11x**) | 59.4 (**2.45x**) |
| 6 | 38.6 (1.01x) | 64.0 (2.27x) |
| 8 | 40.4 (0.97x) | 61.3 (2.37x) |
| 12 | 52.1 (0.75x) | 66.7 (2.18x) |
| 16 | 53.0 (0.74x) | 67.8 (2.15x) |

**教訓**: 並列領域 1 回あたり数 10 us のスレッド起動コストがある。
1 ステップで 15-20 回カーネルを呼ぶので、格子が小さいほどこの固定費
が支配的になる。スレッドを増やすと 1 回の起動コスト自体が増える
ので、小さい問題では少ないスレッドが最適になる。「コアが 64 あるから
64 スレッド」は最悪の選択になりうる。

## 3. 実装

`S2MFD/physics/_jit.py`:

```python
PARALLEL = os.environ.get('S2MFD_PARALLEL', '0') not in ('0','','false','False','no')

def kernel(**kwargs):
    return njit(fastmath=False, parallel=PARALLEL, **kwargs)
```

`prange` は `parallel=False` のとき numba が `range` に落とすので、
**コードは 1 つのまま**逐次と並列の両方を取れる。カーネル側は外側
ループを `prange` にして `@kernel()` を付けるだけ。

### 並列化してよいカーネルの条件

`prange` にするのは **反復間に依存のない、要素ごとの書き込みだけ**の
ループに限る。これを守れば浮動小数点の加算順序が変わらないので、
**結果はスレッド数によらずビット単位で同一**になる。

対象にしたもの (21 ループ):

- `conservative`: `face_average_r/th`, `add_flux_divergence`,
  `add_flux_divergence_scaled`, `add_flux_work`
- `hydro`: `mass_rhs`, `angular_momentum_rhs`, `momentum_rhs`,
  `viscous_meridional_rhs`, `entropy_rhs`, `add_dissipative_heating`,
  `add_ohmic_heating`, `to_primitive_om1/ro1`
- `artdif`: `sld_flux_r/th`, `sld_diffuse_primitive`,
  `sld_diffuse_meridional`, `hyper_flux_r`, `hyper_diffuse_r`,
  `hyper_diffuse_r_primitive`

### 意図的に対象外にしたもの

| カーネル | 理由 |
|---|---|
| `cell_integral` | Neumaier 補正加算。**総和の順序が保存量の機械精度を決める**。並列化すると `dM/M = 1.9e-18` が壊れる |
| `cfl_dt` | スカラーへの min リダクション。安いので触らない |
| `sld_diffusivity_max` | 同上 (max) |

## 4. ソルバ全体での実測

`bench_par.py` (乱数初期値から 400 ステップ、他ジョブ実行中):

| 格子 | 逐次 | 2 | 3 | 4 | 6 | 8 スレッド |
|---|---|---|---|---|---|---|
| 64x64 | 2.895 | **2.223** | 3.297 | 3.370 | 4.026 | 4.852 ms/step |
| 108x144 | 10.955 | 6.337 | **5.060** | 5.251 | 6.450 | 6.158 ms/step |

**チェックサム (`sum|om1|`, `sum|vth|`) は全モードで 17 桁完全一致**。
テストは逐次・4 スレッドの両方で 152 件通過。

カーネル単体の 2.45x に対しソルバ全体は 2.17x どまりなのは、
上記のとおり rhs の約半分が numpy レベルのオーバーヘッドで、そこは
並列化されていないため (アムダール)。numpy 部分を njit に落とせば
さらに伸びる余地がある。

## 5. 使い分けの指針

| やりたいこと | 推奨 |
|---|---|
| 64^2 のパラメタスキャン (表1 の 7 ケースなど) | **逐次 x プロセス並列**。64 コアあるので 7 本同時でも 1 本あたり 2.4 ms/step とほぼ劣化なし |
| 108x144 の本番ラン | `S2MFD_PARALLEL=3` |
| 256^2 以上 | スレッドを増やす価値がある (258x290 で 64 スレッド 5.98x) |

実際に 2026-08-20 の Rempel 表1 再現では、64^2 の 7 ケースを逐次で
同時投入し、108x144 の参照ランだけ 3 スレッドで並行させた。
