# time_marching 高速化の記録

- 日付: 2026-08-19
- ブランチ: `feature/speedup-time-marching`
- 対象: レビュー報告書 §5-3「time_marching の njit 化 / 一時配列削減」(将来課題として挙げていたもの)
- 測定環境: **paris** (AMD EPYC 9354 32コア × 2ソケット, Zen 4), Python 3.12 / numpy 2.5.2 / numba 0.67.0

## 結論

本番設定 (80年スピンアップ + 52年窓, 128×128格子) の**1個体評価が 51.7 秒 → 3.6 秒 (14倍)**。
物理量は変わらない (下記「等価性の検証」)。

## 何が律速だったか

プロファイルの結果、`time_marching` が実行時間の **90%** を占めていた。
さらに内側ループを数えるとセルあたり**約40回の除算**があり、

    16,900セル × 40除算 × 約4.5サイクル ÷ 3.8GHz ≈ 0.8 ms/substep

が実測 0.775 ms/substep とほぼ一致した。つまり**除算スループット律速**であり、
当初想定していた「一時配列によるメモリ帯域律速」ではなかった。

この診断は次の観測とも整合する:

| 実装 | 速度 | 対現行 |
|---|---:|---:|
| 参照実装 (main) | 0.775 ms/substep | 1.00x |
| ループ融合のみ (演算は同一) | 0.747 ms | 1.04x |
| 融合 + numba fastmath | 0.182 ms | 4.26x |
| 除算 → 逆数乗算 | 0.051 ms | 15.1x |
| 逆数 + fastmath | 0.044 ms | **17.7x** |

構造だけ変えても 1.04 倍にしかならず、除算を減らした瞬間に 15 倍になる。

## 実施した最適化

1. **除算の削減** — `1/drr`, `1/r`, `1/r²`, `1/sinθ`, `1/sin²θ` を事前計算し、
   除算を乗算に置き換えた。非局所α効果の係数 `b/(1+b²)` は θ のみに依存するので
   1D 配列として毎 substep 1 回だけ計算する。
2. **numba fastmath の有効化** — FMA と再結合が使えるようになる。
   *注*: 当初 `cache=True` を付けていたため、ファクトリ関数で生成した
   fastmath 版と非 fastmath 版がキャッシュキーを共有してしまい、
   「fastmath が効いていない (結果がビット一致する)」という誤った観測が出た。
   キャッシュを外して初めて正しく測れた。
3. **内側ループからの分岐排除** — 境界セルのゼロ埋め判定を別ループに追い出し、
   内部セルを分岐なしにしてベクトル化を可能にした。
   α効果の種別 (局所/非局所) と境界条件の種別は**コンパイル時に特殊化**する。
   実行時分岐を内側ループに残すと 2.4 倍遅くなることを実測で確認した。
4. **時間積分ループの numba 化** (`S2MFD/physics/stepping.py`) —
   1 ステップ 0.6 ms のうち 0.48 ms が Python↔numba のディスパッチ
   (引数20個超の型検査) だった。「出力時刻まで進める」ループごと numba に入れ、
   Python 側の呼び出しを出力間隔 (40日 ≒ 24ステップ) に 1 回へ減らした。
   スピンアップの極小検出ループも同様に numba 化した。
5. **potential 境界条件の作用素化** — ルジャンドル射影と外部ポテンシャル場による
   再構成は Aφ について線形なので、両者を合成した 1 つの行列
   (`Legendre.build_potential_operator`) を事前計算し、毎ステップの
   (lmax-1, jx) 一時配列生成と冪計算を行列ベクトル積 1 回に置き換えた。
   行列アクセスは連続方向が内側になるようループ順を選んである
   (逆順だとストライド 1 KB になり遅い)。
6. **作業配列の再利用** — `np.empty_like` をループ外に出し、
   1 ステップあたり 135 KB × 4 回の確保をなくした。
7. **背景場の rank-1 分解** — `urr, uth, et, etrr, omth, so` はいずれも
   f(r)·g(θ) の形に分解できる (同梱の全プロファイルで確認)。
   130×130 の 2D 配列 6 本の読み出しを 1D 配列に置き換え、
   メモリトラフィックを約半分にした。分解できない場合は自動的に
   2D 配列を使う一般版カーネルにフォールバックする。
8. **GA ワーカーのコア固定と事前コンパイル** —
   個体評価は多数プロセス同時実行でメモリ帯域律速になるため、
   `os.sched_setaffinity` で 1 プロセス 1 コアに固定すると 1.4 倍速くなる。
   また GA は世代ごとに fork でワーカーを作るので、親プロセスで
   `DynamoProblem.warmup()` を呼んでコンパイル済みコードを継承させる。

## 等価性の検証

`cfg.exact_arithmetic = True` を指定すると、参照実装
`physics.time_marching_reference()` と**ビット一致**する経路になる
(演算順序も背景場の扱いも参照実装と同一)。既定の高速経路との差は:

| 検証項目 | 結果 |
|---|---|
| 1 substep の相対差 (4プロファイル) | 1.0e-16 〜 5.0e-16 (倍精度 1 ULP 程度) |
| 4,700 ステップ積分後の磁場 | 相対差 6.8e-16 (**増幅しない**) |
| 黒点数時系列の相互相関 | 1.000000000000 |
| 適応度 (対観測) | 小数 10 桁まで一致 |
| ステップ数 | 完全一致 |

摂動が増幅しないのは、この系が磁気拡散を含む散逸系でリミットサイクルに
引き込まれるため。カオス的に発散する系ではないことを実測で確認した。

回帰テストは `tests/test_kernel_equivalence.py` (18テスト)。
既存の 92 テストと合わせて **110 テスト**が通る。

## 途中で見つかったバグ

- **局所α効果 (`alpha_type='normal'`) のソース項がゼロになる回帰**を、
  既存のゴールデンテストが検出した。非局所α用に `b/(1+b²)` を 1D 配列へ
  事前計算する最適化を、局所αにも適用してしまったのが原因
  (局所αは `Bph[i,j]` に依存するので 1D にできない)。
  テストがなければ「なんとなく結果が変わった」で済まされた可能性が高い。
  回帰防止テストを追加済み。
- **`exact_arithmetic` のビット一致が rank-1 分解で崩れた**。
  `so_u[i]*so_v[j]` は `so[i,j]` とビット一致しないため、
  exact 経路では 2D 配列をそのまま使うようにした。

## アーキテクチャを跨いだ再現性

同一シードのフルスケール推定を boston (Intel Xeon Gold 6326, Ice Lake) と
paris (AMD EPYC 9354, Zen 4) で並行実行したところ、

- 推定パラメタ `as_u = 831.054412671157`, `ae_u = 839.0965278651761` が **16桁一致**
- twin experiment Step 1 の適応度 `0.875368`、u0 誤差 `5.77%` が一致

計算機とベンダを跨いでも結果が再現することを確認した (最適化前のコードでの比較)。

## 並列スケーリング (最適化の打ち止め判断)

最適化後のコードで、同時実行数を変えて 1 個体あたりの所要時間を測った
(paris の空きコアにプロセスを固定して測定):

| 同時実行数 | 1個体 | 1並列比 |
|---:|---:|---:|
| 1 | 0.97 秒 | 1.00x |
| 2 | 0.97 秒 | 1.00x |
| 4 | 0.96 秒 | 0.99x |
| 8 | 0.97 秒 | 1.00x |
| 16 | 1.02 秒 | 1.06x |
| 24 | 1.05 秒 | 1.09x |

**24 並列でも劣化は 9% にとどまり、ほぼ線形にスケールする。**
したがって最適化後のカーネルはメモリ帯域律速ではなく計算律速であり、
これ以上メモリトラフィックを削っても意味がない。

(最適化の途中で「30 並列だと 1 個体 7〜9 秒」という測定が出たが、
これは別の推定ジョブが同時に 30 コアを使っていて実質 60 並列だったため。
測定時は他ジョブの有無を必ず確認すること。)

## 残る改善余地 (優先度は低い)

- `omrr` だけが 2D のまま (om = A(r) + B(r)·C(θ) なので rank-2 分解が必要)。
  上記のスケーリング結果から、実行時間への寄与はほぼないと見込まれる。
- カーネル単体はベクトル化ピークの約 5 割。さらに詰めるには SIMD 
  レベルの作り込みが要るが、費用対効果は低い。
- 時間刻みは拡散の CFL で決まっている (dt ≈ 1.7 日)。
  陰解法や super-time-stepping を使えばステップ数自体を減らせるが、
  数値スキームの変更になるため本記録の範囲外。
- スピンアップ 80 年が 1 個体の約 6 割を占める。手法上必要だが、
  推定区間を連続的に繋ぐ (論文 5.1 章の将来課題) 実装ができれば
  区間ごとのスピンアップが不要になり、さらに大きく短縮できる。
